## 三条阅读路线

1. **先运行一次**：安装文档 → 普通客户端示例 → 流式示例 → 开发文档中的定向验证。
2. **接入自己的程序**：接口 → 配置 → 工作负载与指标 → 排错。先确定哪些调用属于同一程序，再决定会话生命周期。
3. **继续改代码**：架构 → 后端说明 → 开发约束 → 对应回归测试。先在固定版本上建立可运行基线，再迁移依赖或扩展模型支持。

## 示例与证据的边界

所有终端命令从仓库根目录执行；真实推理命令使用对应 Linux/WSL 后端环境。`/absolute/path/to/model` 是需要替换的占位路径；小模型示例不是任意 GPU 或任意大模型的推荐配置。

代码块中的 Python 示例区分“可独立运行的完整脚本”和“已有服务的客户端”；创建引擎的脚本必须保留 main 保护。文档中的输出字段表是结构说明，不是新一次测试的测量数据。

一次测试通过只证明该环境、模型和用例下的行为。跳过的 GPU、Torch 或 HTTP 测试不算通过；同一 GPU 上运行双副本不等于多 GPU TP 验证。

## 文档维护原则

同一信息只保留一个主要维护位置：安装步骤在 getting-started，字段在 api，参数在 configuration，算法和状态在 architecture，验证要求在 development。README 仅保留快速入口，后端 README 记录该后端的特殊限制。

修改接口、默认值、输入格式或测试开关时，在同一个提交中修改对应文档和示例。文档不能替代版本检查、输入校验或真实 GPU 验证；尚未支持的功能应明确写出，不能仅通过修改措辞声明完成。
